# Session Report: 2026-04-12 (Run 2 + Run 3)

## Summary

Two training runs (Run 2 = ACE+GTSinger, Run 3 = full mixed including UTAU/Kiritan/Itako),
followed by audio A/B testing that revealed **GTSinger as a fundamental data quality
problem source**. Decision to drop GTSinger entirely from v2.

## Run 3: Full Mixed + Upsampling

- Same architecture (5L+6det, 53.6M params)
- Batch size: 128 → 112 (better throughput; 128 had spillover)
- max_frames: 1200 → 800 → **500** (fixed VRAM blowup from long GTSinger sequences)

## Decision: Drop GTSinger Entirely

### Evidence Pattern
| Era | Has GT? | ZH | EN | JA | Outcome |
|---|:-:|---|---|---|---|
| v1 pre-GT | No | OK | n/a | n/a | clean |
| v1 post-GT | Yes | degraded | bad | bad | GT broke things |
| v2 Run 1 | No | clean | n/a | n/a | proves ACE-only works |
| v2 Run 2 | GT en/ja | OK (from ACE) | bad | bad | GT didn't help |
| v2 Run 3 | GT + UTAU/Kiritan/Itako | OK | bad | inconsistent | GT polluted ja, broke en |

**Hypothesis**: GTSinger has fundamental data issues (label timing, ARPAbet→IPA mapping
edge cases, mumble singing styles, or some combination). Empirically, every time GT is
introduced, the corresponding language degrades.

### Action
- Archived all GTSinger preprocessed data → `archive/gtsinger_processed_dropped/`
- Updated config to exclude GTSinger entirely
- Added new clean JA dataset (ONIKU) to compensate

## New Data: ONIKU_KURUMI_UTAGOE_DB

**Source**: https://onikuru.info/db-download/  
**Author**: 御丹宮くるみ (Oniku Kurumi) — **attribution required when used**

### Specifications
- **Singer**: 1 female (Oniku Kurumi)
- **Songs**: 56 (all public-domain, mainly 童謡 nursery rhymes)
- **Voiced duration**: ~61 minutes (excluding pau/br/cl/sil)
- **Format**: HTK 100ns labels, 96kHz/24bit audio
- **Phoneme system**: Standard OpenJTalk (a/i/u/e/o, A/I/U/E/O for devoiced, k/s/t/n/...,
  cl for geminate, N for moraic ん)

### Important Caveats
- ⚠️ **Pitch-corrected and noise-removed** by the author. F0 will be cleaner than natural
  human singing → useful for f0_l1 but won't teach model natural vibrato.
- Some songs have minor clipping (de-clipped, listed in MUSIC_LIST.pdf)
- Includes "spell singing" (nonsense syllables) for CVVC phoneme coverage

### Why It's Better Than GTSinger
- Single-singer (no multi-distribution problem)
- HTK labels (machine-aligned, consistent timing)
- Designed for SVS training (CVVC coverage)
- Author-validated (released as Sinsy-compatible DB)

### Preprocessing Output
- 738 training segments
- 184,076 frames at 50fps
- **1.02 hours** (post-segmentation, after dropping <1.5s and >12s chunks)

## Open Issues / Next Steps

### Long-tail problems (from Run 3 listening tests, not addressed yet)
1. **长尾跑调** (pitch drift on sustained notes): F0 predictor averages, can't model vibrato
   → **Solution chosen**: Outlier filter on F0 loss (mask |dev|>200c frames)
2. **长尾口胡** (mumbling on long notes): det_head averages over sustained-note variations
   → **Solution chosen**: Position encoding in LengthRegulator (intra-note position 0-1
     + note duration as features)

### EN handling
- Currently no EN training data
- Inference on EN songs will have to rely on IPA-based fallback (zh/ja phonemes)
- EN-specific phonemes (/θ/, /ð/, /æ/, /ɹ/) won't be learned at all
- **Future work**: integrate NUS-48E or other clean EN dataset

### Run 4 plan
- Same architecture as Run 3 (5L+6det, 53.6M params)
- Add: position encoding in LengthRegulator
- Add: outlier filter for F0 loss (|dev|>200c → 0.1× weight)
- Maybe: reduce voicing_bce weight from 0.2 → 0.05 (limit voicing overfit)
- Data: ZH (ACE) + JA (UTAU + Kiritan + Itako + ONIKU)
- Weighted sampling: zh×1.0, ja×~2.5 (since en is gone, no en weight needed)
- From scratch (architecture changed: LengthRegulator now takes new inputs)
